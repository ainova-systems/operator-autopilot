# Repoint the D-503 ESLint guard at `engine/pipeline/composers`

## Problem

The D-503 boundary guard in `eslint.operator.config.js:77-94` is scoped to
`files: ["engine/pipeline/stage-logic/**/*.ts", "engine/pipeline/run-stage.ts"]`.
`engine/pipeline/stage-logic/` no longer exists — the layer was renamed to
`engine/pipeline/composers/`. The first glob matches zero files, so the guard
is unenforced across the entire composer layer. `grep -c composers eslint.operator.config.js`
returns `0`.

The gate is dead **twice over**. Even with the glob fixed, neither selector matches
the idiom composers actually use:

- `:83` — `MemberExpression[object.name='vcs'][property.name='getCheckRuns']`.
  For `deps.vcs.getCheckRuns(1)` the outer `MemberExpression` has
  `object.type === "MemberExpression"`, so `object.name` is `undefined` → no match.
- `:88` — `MemberExpression[object.name='deps'][property.name='vcs'] > Identifier[name='getCheckRuns']`.
  `getCheckRuns` is the property of the *outer* `MemberExpression`, not a direct
  child of the `deps.vcs` node → no match.

Composers are exactly the files that reach for `deps.vcs.*` today
(`closed-pr-recovery.ts:159` `deps.vcs.getComments`, `:213` `vcs.getCodeReviews`),
so a composer adding `deps.vcs.getCheckRuns` passes `npm run lint` while bypassing
the `observeChecks` / `writeChecksContextFile` primitives the rule exists to protect.
The comment at `:70-76` claims the rule prevents "future contributors from quietly
bypassing the architecture" — it currently cannot.

Separately, the `no-restricted-imports` message at `:53` points violators at
`agents/workflow/stages.yaml`; neither `agents/` nor `engine/agents/workflow/`
exists. The real path is `engine/content/prompts/stages.yaml`.

## Solution

1. In `eslint.operator.config.js`, change the D-503 `files` array at `:78` to
   `["engine/pipeline/composers/**/*.ts", "engine/pipeline/run-stage.ts"]`
   (keep `run-stage.ts`).
2. Fix the selectors so both `vcs.getCheckRuns(...)` and `deps.vcs.getCheckRuns(...)`
   are caught. Recommended: replace the two selectors with a single
   `MemberExpression[property.name='getCheckRuns']`, which covers every receiver
   shape inside the guarded scope. If you prefer to keep two selectors, the
   deps-form must be
   `MemberExpression[object.type='MemberExpression'][object.property.name='vcs'][property.name='getCheckRuns']`.
   Whichever shape you pick, the regression test below is the arbiter.
3. Update the block comment at `:70-76` and both restriction messages (`:85`, `:90`)
   to say "Composers" / "Composer code" instead of "Stage-logic".
4. Correct the `no-restricted-imports` message at `:53` to name
   `engine/content/prompts/stages.yaml`.

Widening the glob is safe on current code: no file under
`engine/pipeline/composers/` calls `getCheckRuns` in any form, so the corrected
gate produces no new lint failures.

## Regression test (required — this is a gate fix, `dev-verification-gates`)

Add `eslint.operator.config.test.ts` at the repo root, colocated with the config
it pins. Root tsconfig excludes `**/*.test.ts` (`tsconfig.json:21`) so it is not
typechecked, and `vitest.config.ts` has no exclude that would skip it — confirm
collection with `npx vitest run eslint.operator.config.test.ts` before finishing.

Use the ESLint 9 programmatic API against the real config file:

```ts
const eslint = new ESLint({ overrideConfigFile: "eslint.operator.config.js" });
const [result] = await eslint.lintText(source, {
  filePath: "engine/pipeline/composers/d503-probe.ts",
});
```

Required test cases, named for the bug scenario (not the function):

- `"a composer calling deps.vcs.getCheckRuns is rejected by the D-503 guard"` —
  source containing `await deps.vcs.getCheckRuns(1);` at a composer path reports
  a `no-restricted-syntax` error. **This test must fail on pre-fix code** (it fails
  twice over: the path is out of scope, and the selector does not match).
- `"a composer calling vcs.getCheckRuns directly is rejected by the D-503 guard"` —
  same assertion for the bare `vcs.getCheckRuns(1)` form.
- `"a composer calling a non-guarded vcs method is accepted"` — source using
  `await deps.vcs.getComments(1);` reports no `no-restricted-syntax` error, pinning
  that the guard did not over-broaden onto the calls `closed-pr-recovery.ts:159`
  legitimately makes.
- `"run-stage.ts stays inside the D-503 guard scope"` — the same violating source
  at `filePath: "engine/pipeline/run-stage.ts"` still errors, pinning that the
  glob widening did not drop the original scope.
