# Log a WARN when route-verdict's work-item reconciliation write fails

## Problem

`FileVerdictRouter.observeAndReconcile` wraps its `kv.get` + `kv.put`
reconciliation in a `try` (opens at `route-verdict.ts:104`) that ends in a
completely empty `catch` at `route-verdict.ts:160-162`. When the
`kv.put("work-items", …)` at line 143 rejects, the stage completes
"successfully" with zero log evidence that `status`, `statusReason`,
`statusSources`, drift flags, and `attemptCount` were never persisted.

`attemptCount` is the bounded-iteration guard (see the comment at
`route-verdict.ts:132-136`) — a silently lost increment lets a failing
work item be re-selected past its configured cap. This violates
`intelligence/rules/typescript.md` §REQUIRED ("every catch-and-continue
branch MUST warn with the reason", "silent success is a bug") and the
observability BLOCKER gate in `migration.md`.

`RouteVerdictDeps` (`route-verdict.ts:43-47`) currently carries no `Logger`,
so the catch has nothing to log to.

## Solution

1. Add `import type { Logger } from "../../logging/logger.js";` and extend
   `RouteVerdictDeps` with `readonly log?: Logger;` (optional, so the
   argument-less `new FileVerdictRouter()` at
   `engine/engine/stage-handlers.ts:225`, the `emitSkipped` callers, and the
   existing tests keep compiling unchanged).
2. Replace the empty catch with a WARN carrying the failing operation, the
   identifiers, and the error reason — mirroring the established in-repo
   pattern at `engine/pipeline/primitives/persist-output.ts:459-463` and
   `engine/pipeline/primitives/observe-status.ts:334-344`:

   ```ts
   } catch (err) {
     deps.log?.warn("route-verdict: work-item reconciliation write failed — continuing best-effort", {
       workItemId, executionId, stage: stageDef.name,
       verdict: agentResult.verdict,
       error: errorMessage(err),
       cause: err instanceof Error && err.cause ? String(err.cause) : undefined,
     });
   }
   ```

   Import `errorMessage` from `@operator/core` (already exported —
   `packages/core/src/errors/index.ts:85`; used the same way in
   `engine/pipeline/cleanup.ts:53`).
3. Add a DEBUG line on the success path immediately after the `kv.put`, so
   the reconcile is auditable either way (matches
   `persist-output.ts:456-458`):

   ```ts
   deps.log?.debug("route-verdict: work-item reconciled", {
     workItemId, status: reconciled.effectiveStatus,
     statusReason: reconciled.effectiveStatusReason,
     hasDrift: drift.hasDrift, attemptCount: nextAttemptCount,
   });
   ```
4. Thread the logger at the single assembly site: `engine/pipeline/run-stage.ts:426`
   currently passes `{ bus: deps.bus, kv: deps.kv }`. Change to
   `{ bus: deps.bus, kv: deps.kv, log: deps.log }`. `RunStageDeps.log` already
   exists at `run-stage.ts:48` and is already threaded to persist-output at
   line 404 — no `entry.ts` change is needed.
5. **Preserve the non-throwing behavior.** The catch must still swallow the
   error so a failed observation never masks the real stage verdict.

## Observability Impact

- **Adds WARN** `route-verdict: work-item reconciliation write failed — continuing best-effort`

  status, reason, drift flag, and `attemptCount`.
- **Removes nothing.** The `STAGE_COMPLETED` / `PIPELINE_FAILED` bus emits and
  every existing log line are untouched.
